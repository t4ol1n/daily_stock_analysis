## What system/approach is used

The application uses a **`.env`-file-backed configuration system** layered on top of `python-dotenv`, with a declarative field registry that drives both server-side validation and the Web UI settings form. The stack consists of:

- **Persistence layer**: `src/core/config_manager.py` — an atomic `.env` reader/writer that parses each line into `ConfigLineEntry` objects, supports optimistic versioning via SHA-256 + mtime hashes, and writes updates by writing to a `.tmp` file then `os.replace`, falling back to in-place rewrite when mounts do not support rename.
- **Runtime loading**: `src/config.py` — loads `.env` via `load_dotenv`, exposes a frozen `Config` dataclass populated from environment variables, and provides typed parsers (`parse_env_int`, `parse_env_float`, `parse_env_bool`) plus LLM channel/model normalization helpers.
- **Field metadata registry**: `src/core/config_registry.py` — a single source of truth defining every supported configuration key with title, description, category, data type, UI control, default value, validation rules, help keys, examples, docs links, and warning codes. Categories include `base`, `ai_model`, `data_source`, `notification`, `system`, `agent`, `backtest`, and `uncategorized`.
- **Service layer**: `src/services/system_config_service.py` — `SystemConfigService` orchestrates read/validate/update/import/export, merges saved `.env` values with process runtime environment (for Docker `--env-file` display), performs LLM channel discovery/test/capability checks, notification channel tests, generation backend smoke tests, and first-run setup status.
- **REST API**: `api/v1/endpoints/system_config.py` — FastAPI router exposing `/config`, `/config/validate`, `/config/import`, `/config/export`, `/config/setup/status`, `/config/generation-backends/*`, `/config/agent-backends/*`, `/config/llm/test-channel`, `/config/notification/test-channel`, `/config/llm/discover-models`, and `/config/schema`.
- **Pydantic schemas**: `api/v1/schemas/system_config.py` — strongly typed request/response models for all config endpoints.

## Architecture and conventions

### Layered configuration model

1. **Source of truth is the `.env` file** located at the repository root (resolvable via `ENV_FILE` or relative to project root). It stores user-editable settings as `KEY=VALUE` lines.
2. **Process environment overrides are merged for display only**. `SystemConfigService._build_runtime_display_config_map` reads `os.environ` and overlays it onto saved `.env` values so Docker `--env-file` / `env_file` injected values appear in the Settings UI without being persisted back to disk.
3. **Every configurable key must be declared in the registry**. Keys not present in `config_registry._FIELD_DEFINITIONS` land in the `uncategorized` bucket and are excluded from schema responses unless they match the `LLM_*_(PROTOCOL|API_SURFACE|BASE_URL|API_KEY|API_KEYS|MODELS|EXTRA_HEADERS|ENABLED)` pattern for active channels declared in `LLM_CHANNELS`.
4. **Validation is declarative**. Each field defines `validation` constraints (e.g. `enum`, `min`, `max`, `format: url`, `multi_value`, `pattern`). `SystemConfigService.validate` runs these against submitted items and returns structured issues with `severity`, `code`, `expected`, `actual`.
5. **Secrets are masked end-to-end**. Sensitive fields are marked `is_sensitive: True` in the registry; server-masked keys (`LLM_HERMES_API_KEY`, `LLM_HERMES_API_KEYS`, `LLM_HERMES_EXTRA_HEADERS`, `LLM_USAGE_HMAC_SECRET`) are always returned as the configured `mask_token`; clients must use `raw_value_exists` and `is_masked` to interpret them.
6. **Optimistic locking via config version**. Every read returns `config_version = f"{mtime_ns}:{sha256(content)}"`. Updates require the same version; conflicts raise `ConfigConflictError` mapped to HTTP 409.
7. **Atomic persistence**. `ConfigManager.apply_updates` builds a new `.env.tmp`, flushes and fsyncs, then `os.replace`s it into place. If rename fails with `EBUSY`/`EXDEV` (common on Docker mounts), it falls back to in-place rewrite.
8. **Compose-safe storage for template placeholders**. `CUSTOM_WEBHOOK_BODY_TEMPLATE` is escaped before write (`$${...}`) and unescaped on read so Docker Compose variable interpolation does not corrupt Jinja-style templates.

### LLM configuration model

- Primary model via `LITELLM_MODEL` in `provider/model` format; optional per-agent override `AGENT_LITELLM_MODEL` inherits from primary when empty.
- Fallback chain: `LITELLM_FALLBACK_MODELS` comma-separated list.
- Advanced routing via `LITELLM_CONFIG` pointing to a LiteLLM-native YAML file; when parseable and yielding a `model_list`, it takes priority over channel/legacy keys.
- Multi-channel mode via `LLM_CHANNELS` plus `LLM_<NAME>_PROTOCOL|BASE_URL|API_KEY|API_KEYS|MODELS|EXTRA_HEADERS|ENABLED` keys, validated through `resolve_llm_channel_protocol`, `normalize_llm_channel_model`, and `apply_litellm_api_surface`.
- Channel test/discovery endpoints perform real network calls to probe `/models` and run minimal completions, reporting capability results for `json`, `tools`, `stream`, `vision`.

### Runtime reload semantics

After a successful update, `SystemConfigService._reload_runtime_singletons` resets module-level singletons (`ToolRegistry`, fetcher manager, search service) so the next agent/chat execution picks up fresh configuration. `setup_env(override=True)` can re-load `.env` into `os.environ` for processes that cache environment values.

## Conventions and constraints

- **All configuration keys are uppercase `KEY=VALUE` pairs** in `.env`; assignment parsing uses `re.compile(r"^\s*([A-Za-z_][A-Za-z0-9_]*)\s*=\s*(.*)$")`.
- **Boolean parsing treats `0`, `false`, `no`, `off` as falsey**; everything else is truthy.
- **Integer/float parsing clamps to configured min/max and logs warnings** rather than raising, returning defaults on invalid input.
- **New fields must be added to `config_registry._FIELD_DEFINITIONS`** to appear in the Settings UI; missing keys fall into `uncategorized`.
- **Hidden-from-UI keys** are listed in `WEB_SETTINGS_HIDDEN_FROM_UI` (database path, SQLite tuning, proxy settings).
- **Sensitive values cannot be overwritten with the mask token** unless they were previously unset; attempts to set a secret to `******` are skipped and reported as `skipped_masked`.
- **Import/export requires admin auth** in non-desktop mode; `DSA_DESKTOP_MODE=true` bypasses this check for desktop packaging compatibility.
- **Schema versioning**: `SCHEMA_VERSION = "2026-06-29-claude-code-cli-backend"` is included in schema responses to allow frontend compatibility checks.
- **Notification channel testing** is restricted to a whitelist (`wechat`, `dingtalk`, `feishu`, `telegram`, `email`, `pushover`, `ntfy`, `gotify`, `pushplus`, `serverchan3`, `custom`, `discord`, `slack`, `astrbot`) with required key groups defined per channel.
- **Generation backend status** distinguishes between cheap pre-flight checks (no network call) and explicit smoke tests (real model call) via separate endpoints and `mode` parameter.
